## 2. 依赖矩阵

```
App ──────────────→ MainWindow, NativeMouse, ScreenHelper
MainWindow ───────→ EdgeWatcher, ProcessManager, TrayIcon, GlobalHotkey, ConfigStore, SettingsWindow
SettingsWindow ───→ ConfigStore, DrawerConfig, AppItemConfig
EdgeWatcher ──────→ DrawerConfig, ScreenHelper
ProcessManager ───→ AppItemConfig
Config ───────────→ (无内部依赖)
TrayIcon / GlobalHotkey / ScreenHelper / NativeMouse ──→ (无内部依赖)
```

**依赖方向规则**：底层模块（`ScreenHelper` / `NativeMouse` / `Config`）不得引用上层；
`EdgeWatcher` / `ProcessManager` / `TrayIcon` / `GlobalHotkey` 之间**互不引用**，统一由
`MainWindow` 编排。这是刻意的隔离——四个"系统能力"模块各自独立，便于单独测试与替换。

`Config` 被 `EdgeWatcher` 依赖是因为 `EdgeWatcher` 需要读停靠边等几何参数。

## 3. 职责边界表

| 文件 | 负责 | 不负责 |
| --- | --- | --- |
| `EdgeWatcher` | 边缘检测、显隐状态机、动画、置顶 | 决定"什么时候该显示"之外的任何策略判断 |
| `ProcessManager` | 进程生命周期 | UI 刷新（只抛事件，不碰控件） |
| `TrayIcon` | 托盘图标与菜单 | 菜单项点击后做什么（抛事件给 `MainWindow`） |
| `GlobalHotkey` | 热键注册与消息接收 | 热键触发什么（抛事件） |
| `MainWindow` | 把上述事件编排成用户可见行为 | 自己做 Win32 调用 |

**模式**：所有"系统能力"模块只**暴露事件**，`MainWindow` 订阅并转成 UI 行为。
不要在 `TrayIcon` 里直接调 `EdgeWatcher`——那是 `MainWindow` 的活。

## 4. 线程边界（**最大的雷区**）

| 触发点 | 所在线程 | 能否直接碰 UI |
| --- | --- | --- |
| `DispatcherTimer` tick | UI 线程 | ✅ 可以 |
| `EdgeWatcher.RevealChanged` | UI 线程 | ✅ 可以 |
| `TrayIcon.ToggleRequested` 等 | **消息窗口线程**（HwndSource 自己的线程 = UI 线程） | ✅ 可以，但**统一走 `Dispatcher.Invoke` 更保险** |
| `GlobalHotkey.Pressed` | UI 线程 | ✅ 可以 |
| **`ProcessManager.Changed`** | **线程池线程**（`Process.Exited` 由系统事件线程触发） | ❌ **绝对不行** |

### 正确写法

```csharp
// MainWindow.xaml.cs —— 订阅处切回 UI 线程
_procs.Changed += () => Dispatcher.Invoke(UpdateStatus);
```

```csharp
// ProcessManager.cs —— 回调只清表 + 抛事件，绝不碰 UI
private void OnProcessExited(Process p)
{
    int pid;
    try { pid = p.Id; } catch { return; }   // 句柄可能已释放
    lock (_lock) _list.RemoveAll(e => e.Proc.Id == pid);
    Changed?.Invoke();
}
```

> **反面教材（历史 bug）**：`p.Exited += (_, _) => { ...; Changed?.Invoke(); }`，
> 而 `Changed` 的订阅方直接 `UpdateStatus()` 改 WPF 控件 → 跨线程异常 → 未处理 →
> **进程崩溃**，表现为「点击启动就崩」。`--launch-test` 自测就是防这个的。

## 5. Win32 P/Invoke 分布

| DLL | 用途 | 所在文件 |
| --- | --- | --- |
| `user32.dll` | `GetCursorPos` / `SetWindowPos` / `RegisterHotKey` / `MonitorFromPoint` / `GetDpiForSystem` / `SetCursorPos` | `EdgeWatcher` `GlobalHotkey` `ScreenHelper` `NativeMouse` `TrayIcon` |
| `shell32.dll` | `Shell_NotifyIcon` | `TrayIcon` |

**所有 P/Invoke 都用 `DllImport` 写在对应模块里**，不建集中封装层——每个模块的 Win32 依赖是它自己的实现细节。

## 6. 代码异味与阈值

| 检查项 | 阈值 | 现状 |
| --- | --- | --- |
| 单文件行数 | > 300 行需拆分 | `MainWindow.xaml.cs` 342 行 ⚠️ **已超**，见 A03 |
| 单类公开成员 | > 15 个考虑拆 | `Config.cs` 中 `DrawerConfig` 9 个属性、`ProcessManager` 8 个，均可接受 |
| 直接 P/Invoke 数 | > 8 个考虑抽模块 | `TrayIcon` 12 个 ⚠️ 已超，但都是托盘必需 |
| 魔法数字 | 出现 2 次以上就提成常量或配置 | `EdgeWatcher` 的 `HotZoneDip`/`HandleDip` 已提取 ✅ |

**已知的两处超标是有意为之**：`MainWindow.xaml.cs` 是 UI 编排中心（拆了反而更难读），
`TrayIcon` 的 Win32 调用是托盘协议的固有复杂度。拆之前先确认收益。

## 7. 反模式

| 反模式 | 为什么坏 | 正确做法 |
| --- | --- | --- |
| 在 `ProcessManager` 里 `Dispatcher.Invoke` 更新 UI | 底层模块耦合 UI，无法独立测试 | 抛事件，由 `MainWindow` 订阅后切线程 |
| 在 `EdgeWatcher` 里 `new MainWindow()` | 循环依赖 | `EdgeWatcher` 只接收 `Window` 引用 |
| 用 `RenderTransform` 做显隐 | 不影响命中测试，隐藏区仍吃点击 | 移动 `Window.Left/Top`（`EdgeWatcher.AnimateTo`） |
| 用 `SystemParameters.WorkArea` 判热区 | 只给主屏，多屏失效 | `ScreenHelper.WorkAreaAtCursorDip()` |
| 在 `EnsureHandle()` 之后订阅 `SourceInitialized` | 事件已同步触发过，永远收不到 | 直接调 `Start()`（见 `MainWindow` 构造末尾） |
| 把 `Tag` 当 transform 载体 | `Tag` 不参与渲染，动画白动 | `RenderTransform`（或本项目用位置移动） |
| 在 `SettingsWindow` 里直接改 `EdgeWatcher` 内部状态 | 设置页与抽屉强耦合 | 改 `DrawerConfig` → `ApplyConfig` 热重载 |
| 硬编码 logo 路径 | logo 目录调整后全丢 | 配置引用 `assets/logos/<name>/logo-rounded.png`，改布局时同步改配置 |
| 拿 `lParam` 整体比 `WM_RBUTTONUP` | **托盘右键完全无反应**（图标在、菜单不出）——NOTIFYICON_VERSION_4 下 LOWORD 才是鼠标消息，HIWORD 是图标 id | `lParam.ToInt64() & 0xFFFF` 只取 LOWORD（见 `TrayIcon.WndProc`） |
| 用 `HWND_MESSAGE` 窗口 `SetForegroundWindow` | 消息窗口不可见，置前不可靠，菜单一点就消失 | 用主窗口 HWND 置前（`TrayIcon._ownerHwnd`） |
